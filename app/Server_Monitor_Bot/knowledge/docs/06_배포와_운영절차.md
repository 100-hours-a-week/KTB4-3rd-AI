# 배포와 운영절차

## 배포 이미지(Dockerfile)

backend-fastapi/Dockerfile은 V2 ECS `fastapi` 서비스용 이미지다.

- 빌드: `docker build -t moyeota-ai .`
- 빌드 인자 EXTRAS: 서버 모니터링 봇은 `EXTRAS=monitor`(CI 기본), 로컬 모델은 `EXTRAS=local`, 함께 쓸 때 `EXTRAS=monitor,local`
- 베이스: `python:3.12-slim`(배포 전 검토한 digest로 고정, CI의 PYTHON_VERSION 3.12와 맞춤). build 단계에서 가상환경(/opt/venv)에 설치하고 runtime 단계로 복사한다.
- 실행 사용자: 비루트 `app`(uid·gid 10001)
- RDS TLS용 AWS 공식 CA 번들을 `/opt/certs/rds-global-bundle.pem`에 넣는다(AI_DB_URL `?ssl=verify`).
- 런타임 값(OpenAI 키 등)은 이미지에 넣지 않는다. ECS 태스크가 SSM `/moyeota/v2/<stage>/ai/*`에서 주입한다.
- 로컬 실행 예: `docker run --env-file .env -p 8000:8000 moyeota-ai`

## 기동 명령과 종료 동작

Dockerfile CMD: `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1 --timeout-graceful-shutdown 50`

- 포트 8000은 ALB 대상 그룹, Service Connect(`http://fastapi:8000`), CI 헬스체크와 맞춘 값이다.
- 워커 1개: 태스크가 0.5 vCPU라 프로세스를 늘리지 않는다.
- exec 형태라 uvicorn이 PID 1로 SIGTERM을 직접 받는다.
- graceful shutdown 50초는 ECS stopTimeout(60초) 안에 진행 중인 OpenAI 호출을 최대한 마무리하려는 값이다.
- 종료 순서(app/main.py): uvicorn이 진행 중인 HTTP 요청을 최대 50초 기다린 뒤, 내부 큐가 새 요청을 거절(503 MODEL_NOT_READY) → 남은 작업을 10초까지 기다림 → 워커 취소 → 못 한 작업은 MODEL_NOT_READY → 모니터 분석 프로세스 종료(최대 12초 대기 후 강제 종료).
- Kafka 워커도 같은 때 멈춘다. 미터기 이미지 분석 워커는 10초만 기다리고, 커밋하지 않은 요청은 다른 태스크가 다시 받는다(BE가 analysis_started_at으로 중복을 거른다).
- 헬스체크: `GET /health`는 프로세스가 떠 있으면 200이다.

## 재시작으로만 바뀌는 상태

코드상 재시작 전까지 고정되는 상태다.

- 이미지 처리 장치(DEVICE: modal, 로컬 장치, off)는 기동 때 한 번 정한다.
- Modal 엔진이 down(토큰 오류, 자동 배포 실패, modal 패키지 없음)이 되면 재시작 전까지 GPU 경로 요청은 luna로 넘어간다.
- 로컬 ocr·slm 준비에 실패한 (모델, 장치)는 down에 들어가 재시작 전까지 luna로만 처리한다.
- Modal 앱은 기동 때 자동 준비된다: 지금 코드 버전 이름의 앱을 찾고, 없으면 그 자리에서 배포한다(첫 빌드는 몇 분). 배포에 성공하면 예열을 1회 한다. 그동안 GPU 경로 요청은 luna가 처리한다.
- 수동 Modal 배포: backend-fastapi 폴더에서 `modal deploy -m app.llm.modal_app`

## 모니터 봇 기동과 리더

- 분석 프로세스는 백그라운드로 뜨며 DB 연결을 기다리지 않는다. AI DB가 중단돼도 API 기동과 헬스체크는 평소와 같다.
- 텔레그램 수신, 일일 작업, 예약 작업은 MySQL `GET_LOCK`을 잡은 태스크 1개(리더)만 한다. 리더가 내려가면 다른 태스크가 이어받는다.
- DB 스키마 버전이 코드 기대값(SCHEMA_VERSION 1)과 다르면 기록 적재만 하고 분석은 멈추며 텔레그램으로 알린다. 10초마다 다시 확인해, 맞으면 재시작 없이 분석을 시작하고 알린다.
- 분석 프로세스가 죽으면 본 서비스의 감시 쓰레드가 다시 띄운다. 10초 뒤에 띄우고, 띄운 지 5분 안에 또 죽으면 대기를 2배씩 늘린다(최대 10분). 새 프로세스는 관리자에게 알리고 `monitor_health.restarts`에 횟수를 남긴다.
- AI DB에 연결하지 못하면 `db connect failed` 경고에 오류 번호와 메시지를 남긴다. 2003 + CERTIFICATE_VERIFY_FAILED는 인증서, 2003 + Name or service not known·시간 초과는 주소·보안그룹, 1045는 계정·비밀번호 문제다.
- 지식 시드와 저장소 문서(P4)는 배포 이미지 태그당 한 태스크가 seed.json과 knowledge/docs/*.md를 검사해 바뀐 것만 Qdrant에 반영한다.
- 보존 정리(P6)는 리더가 매일 기간 지난 행을 5,000건 단위로 지운다.
- TELEGRAM_BOT_TOKEN은 동시에 1개 스테이지만 활성화한다. dev → stg → prod 순으로 검증한 뒤 최종 prod에 고정한다.

## 설치 스크립트(install)

모니터 설치 스크립트다. 실행: `python -m app.Server_Monitor_Bot.install`

기본 실행 순서:
1. 환경변수 이름 확인
2. MySQL 스키마: 없을 때만 만든다
3. Qdrant 컬렉션 knowledge, docs, chat 준비
4. 지식 시드 적재와 저장소 문서(repo docs) 동기화
5. 요약 출력. 실패가 있으면 종료 코드 1

옵션:

| 옵션 | 동작 |
| --- | --- |
| `--check` | 읽기 전용. 개수만 센다 |
| `--reembed` | 임베딩 모델·차원을 바꾼 뒤 쓴다. knowledge·docs payload를 `buffer_dir/reembed-<날짜>.json`으로 백업 → 컬렉션 재생성 → 다시 임베딩. chat 컬렉션은 매일 도는 P6이 다시 만든다 |

## Qdrant 컬렉션과 백업

- 컬렉션 이름은 `<stage>_<이름>`이다: `<stage>_knowledge`, `<stage>_docs`, `<stage>_chat`(store/vector.py).
- knowledge(장애 지식)와 docs(올린 문서)는 원본이 Qdrant에만 있다. 그래서 Qdrant 일일 스냅샷이 필요하다.
- chat은 MySQL 대화 원문의 색인이다.
- 거리 함수는 코사인, 벡터 차원은 설정 model.embedding_dim(1536)이다.
- Qdrant 운영 요구: API 키 인증 필수, 6333 포트만, FastAPI 태스크 보안그룹에서만 접근 허용, 초기 사양 메모리 1GB·디스크 10GB(클라우드 전달 문서).

## 클라우드팀 요청·회신 항목

클라우드 전달 문서의 작업 요청 항목이다.

- RDS AI 전용 DB·계정 생성: 스테이지별 `ai_dev`, `ai_stg`, `ai_prod`(계정 이름도 같음). 권한은 해당 DB 한정 SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP.
- DB 이름은 반드시 `ai_<stage>`여야 한다. 다르면 모니터가 켜지지 않는다(서비스 영향 없음).
- Qdrant 구축·운영, 스테이지별 접속 주소·API 키 발급
- 보안그룹: dev·stg·prod FastAPI 태스크 SG에서 RDS TCP 3306, Qdrant TCP 6333 허용
- SSM 파라미터 등록 후 태스크 정의에 연결하고 재배포
- 애플리케이션 런타임 중에는 DDL을 실행하지 않는다. 스키마 생성·변경은 AI 담당자가 발급된 계정으로 한다.
- 컨테이너 `/tmp`에 최대 약 100MB를 쓴다(readonlyRootFilesystem 확인 항목).

## 근거 문서에 없는 절차

아래 절차는 근거 문서(클라우드 전달 문서, Dockerfile)에 적혀 있지 않아 문서화되지 않은 상태다.

- 서비스 배포 롤백 절차
- OpenAI 키, Modal 토큰, 텔레그램 토큰, DB 비밀번호 교체(로테이션) 절차
- 서비스 재시작 명령(ECS 조작 방법)

근거 문서에 있는 관련 사실:
- 시크릿은 SSM SecureString으로만 관리하고 메신저·문서로 공유하지 않는다.
- 텔레그램 토큰 등록 방식(AI 담당자 직접 등록 또는 클라우드팀 등록)은 클라우드팀 회신 항목(A6)이다.
- 조정(runtime 플래그)의 원복은 모니터 봇 [즉시 원복] 버튼과 TTL 만료로 한다(07_조정_정책표 참고).
