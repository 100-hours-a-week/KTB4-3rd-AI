# Spring ↔ FastAPI 혼잡도 분석 연동 제안

작성일: 2026-10-21

상태: **AI의 현재 구현 기준 제안. Spring 승인 전 계약이다.**

## 역할과 호출

Spring은 스팟에 속한 원글·댓글의 현재 전체 데이터를 조회하고 `POST /congestion-analyses`로 보낸다. FastAPI는 받은 스팟을 매번 분석하며 요청 간 판정 캐시나 Spring 콜백을 사용하지 않는다. Spring은 결과를 저장·조회·만료하고 필요할 때 다시 요청한다. AI는 Spring의 조회 누락이나 스팟 배정 오류를 확인할 수 없다.

사용자가 정한 산출 방향은 **출퇴근시간대 10분마다, 그 외 60분마다 변경·만료된 스팟 요청**이다. 요청에는 해당 집계 창을 `window_minutes=10` 또는 `60`으로 명시한다. 출퇴근 시각·기준 시간대·전환 첫 요청의 창은 Spring과 합의해야 한다. AI는 `as_of - window_minutes < created_at <= as_of`만 집계한다. 오래된 원글에 창 안의 새 댓글이 있으면 부모 원글과 댓글 전체를 문맥으로 함께 보낸다.

현재 기본 분석 경로는 시간 선별 → 관련성 분류 → 스팟별 개별 판정 → 코드 집계·요약이다. 요청 안에서 스팟 최대 3개를 병렬 처리하고 결과 순서는 요청 순서다.

## 요청 형식

모든 필드는 필수다. `null`, 추가 필드, 공백만 있는 문자열은 받지 않는다. ID는 양의 JSON 정수다.

| 위치 | 필드 | 허용값·의미 |
| --- | --- | --- |
| 최상위 | `request_id` | 1~128자 문자열. Spring이 부여하고 AI가 응답 본문에 그대로 반환한다. UUID는 강제하지 않는다. |
| 최상위 | `as_of` | 모든 스팟에 공통으로 적용한 조회 기준 시각. 시간대가 있는 ISO 8601 문자열. |
| 최상위 | `window_minutes` | JSON 정수 10 또는 60. |
| 최상위 | `spots` | 1~20개. `spot_id`는 요청 전체에서 유일하다. |
| 스팟 | `post_bundles` | 0~50개. 빈 목록은 **조회에 성공했지만 제보가 없음**을 뜻한다. 조회 실패의 대용으로 보내면 안 된다. |
| 원글 | `post_id`, `title`, `content`, `author_key`, `created_at`, `comments` | 제목 1~30자, 본문 1~280자, 작성자 키 1~128자, 댓글 0~100개. |
| 댓글 | `comment_id`, `content`, `author_key`, `created_at` | 본문 1~280자, 작성자 키 1~128자. |

`post_id`는 요청 전체의 원글끼리, `comment_id`는 댓글끼리 중복될 수 없다. 두 종류 사이에는 같은 숫자를 쓸 수 있다. 원글·댓글의 `created_at`은 시간대가 있는 ISO 8601 문자열이어야 하고 `as_of`보다 미래면 안 된다. 요청 전체의 원글+댓글은 최대 1,000개다. 한도를 넘으면 부분 분석 없이 전체 422다.

`author_key`는 같은 작성자가 원글·댓글과 서로 다른 요청에서 같은 값을 가져야 작성자별 중복 집계가 안정적이다. 아래 값은 생성 방식이 확정되지 않은 가상 예시다.

```json
{
  "request_id": "congestion-20261021-1800-01",
  "as_of": "2026-10-21T18:00:00+09:00",
  "window_minutes": 10,
  "spots": [
    {
      "spot_id": 101,
      "post_bundles": [
        {
          "post_id": 20481,
          "title": "역 앞에 사람이 많아요",
          "content": "지금 역 앞에 사람이 많고 대기줄이 길어요.",
          "author_key": "member_4821",
          "created_at": "2026-10-21T17:55:00+09:00",
          "comments": [
            {
              "comment_id": 50931,
              "content": "저도 지금 줄을 서 있어요.",
              "author_key": "member_7310",
              "created_at": "2026-10-21T17:57:00+09:00"
            }
          ]
        }
      ]
    },
    {"spot_id": 102, "post_bundles": []}
  ]
}
```

## 응답과 실패

유효한 요청은 스팟별 성공과 실패가 섞여도 HTTP **200**이다. 요청한 스팟을 같은 순서로 한 번씩 반환한다. 성공 결과의 `congestion_level`은 `LOW | MEDIUM | HIGH | UNKNOWN`, `report_count`는 유효한 혼잡 단계 투표에 반영된 서로 다른 작성자 수다. `summary`는 최종 집계 값으로 만든 비공백 문장이다.

구체 원인 코드는 `RUSH_HOUR`, `EVENT`, `ACCIDENT`, `BREAKDOWN`, `DELAY`, `SERVICE_DISRUPTION`, `WEATHER`, `ROAD_TRAFFIC`, `CONSTRUCTION`, `DEMONSTRATION`이다. 원인별 `report_count`도 서로 다른 작성자 수다. 유효한 단계 제보가 있지만 구체 원인이 전혀 없으면 원인 `UNKNOWN` 0명을 넣는다. 유효한 단계·원인이 모두 없으면 단계 `UNKNOWN`, 혼잡 제보자 0명, 원인 빈 목록이다. 단계 동률도 `UNKNOWN`이므로 한산함을 뜻하지 않는다.

다음은 **응답 구조 예시**이며 위 입력의 실제 모델 판정을 보증하지 않는다.

```json
{
  "request_id": "congestion-20261021-1800-01",
  "spots": [
    {
      "spot_id": 101,
      "analysis_status": "SUCCESS",
      "result": {
        "congestion_level": "MEDIUM",
        "report_count": 2,
        "causes": [{"cause_code": "UNKNOWN", "report_count": 0}],
        "summary": "제보 기준 혼잡도는 보통이며, 혼잡 제보자는 2명입니다. 구체적인 혼잡 원인은 제보되지 않았습니다."
      }
    },
    {
      "spot_id": 102,
      "analysis_status": "SUCCESS",
      "result": {
        "congestion_level": "UNKNOWN",
        "report_count": 0,
        "causes": [],
        "summary": "혼잡 단계를 판단할 유효 제보가 없습니다."
      }
    }
  ]
}
```

모델 호출·출력 검증 등 스팟 분석만 실패하면 해당 항목은 `{"spot_id":101,"analysis_status":"FAILED","result":null,"code":"ANALYSIS_FAILED","message":"analysis failed"}`다. 다른 스팟은 계속 처리하고 같은 요청 안에서 자동 재시도하지 않는다. Spring은 HTTP 200만 보지 말고 **각 `analysis_status`**를 확인해야 한다.

필드 누락·형식 오류·중복 ID·규모 초과 등 요청 자체의 오류는 전체 HTTP **422**, 본문 `{"success":false,"code":"REQUEST_INVALID","message":"request is invalid"}`다. 예상하지 못한 서버 오류는 공통 오류 응답으로 처리한다. 응답 본문에는 `as_of`나 마지막 제보 시각이 없다.

## 집계 정책

- 작성자별 최신 유효 단계 제보에 한 표를 준다. 최다 표 동률은 `UNKNOWN`이다. 작성 시각이 같으면 댓글을 원글보다 최신으로, 같은 종류끼리는 큰 ID를 최신으로 본다.
- 원인은 단계와 별도로 작성자별 최신 유효 제보에서 고른다. 그 제보에 원인이 없으면 이전 원인을 버린다. 원인만 제보한 작성자는 단계 `report_count`에는 포함하지 않는다.
- 오래된 부모 원글은 새 댓글의 문맥이 될 수 있지만 자체 제보로 집계하지 않는다. 부모의 원인을 댓글 작성자에게 자동 부여하지 않는다.
- 제보 부족은 한산함의 증거가 아니다. 빈 스팟과 유효 제보 없음은 `LOW`가 아니라 `UNKNOWN`이다.

## Spring과 결정할 사항

| 우선 | 확인·결정할 질문 | 필요한 이유 |
| --- | --- | --- |
| 필수 | 출퇴근 시작·종료 시각과 시간대, 전환 첫 요청의 조회 범위·`window_minutes`는? | 주기 경계의 제보 누락 방지 |
| 필수 | 창 안의 전체 글·댓글과 오래된 부모를 제공할 수 있는가? 수정·삭제·조회 실패와 빈 결과를 어떻게 구분하는가? | 부분 데이터는 AI가 감지할 수 없음 |
| 필수 | 안정적인 `author_key`와 `request_id`를 어떻게 생성하는가? | 작성자 집계·요청 추적 |
| 필수 | 역·승강장·도로 등 글의 `spot_id` 배정 기준은? | AI는 받은 스팟을 재배정하지 않음 |
| 필수 | 평소·최대 입력량, 응답 대기시간, 타임아웃·응답 유실 후 재요청 방식은? | 전체 마감·상한 초과 정책 결정 |
| 필수 | 스팟 `FAILED`, 전체 422·5xx, 응답 유실 때 이전 결과를 유지·숨김·만료 중 어떻게 처리하는가? | 오래된 결과의 현재값 오인 방지 |
| 운영 | 요청 중 새 변경과 같은 스팟의 중복·역순 응답을 어떻게 처리하는가? | 최신 결과 덮어쓰기 방지 |
| 운영 | 실제 URL·서버 간 인증·`X-Request-ID` 헤더는? | 배포 호출과 양쪽 로그 대조 |

## 배포 전 확인

혼잡도 OpenAI 키 `OPENAI_API_KEY_2`는 배포 환경에 넣어야 한다. 관련성 임계값 0.2·0.8과 Decisions 동작별 타임아웃 30초는 `app/features/congestion/config.py`에 모아 둔 **합성 평가용 임시값**이다. 실데이터 검증과 Spring의 응답 대기시간 합의 후 운영값을 확정해야 한다. 키가 없으면 후보가 있는 스팟은 실패한다.

최근 판정 규칙 변경 후 실모델 재평가와 실제 게시글 라벨 검증은 남아 있다. AI에는 요청 전체의 확정 마감 시간, 요청 간 전역 동시성 상한, 큰 스팟 입력 분할이 없다. Spring의 응답 대기시간과 실제 입력량을 받은 뒤 이 수치를 정해야 한다. 이미지 분석의 60초 대기시간을 혼잡도 계약에 자동 적용하지 않는다.
