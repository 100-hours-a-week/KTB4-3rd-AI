# 혼잡도 합성 평가 데이터셋 v1

## 목적과 현재 상태

사용자는 경계 표현의 판정을 추후 고도화로 미루고, 확정 기준의 정답셋으로 정확도·속도·입력량을
측정하는 방향을 선택했다. 이 버전은 그에 따른 신규 합성 데이터다. 60시나리오와 입력량 5종은
평가 초안을 위한 구성값이며 제품 정책·운영 최대량·성능 목표를 새로 확정한 것이 아니다.

- 모델 결과를 정답으로 사용하지 않았다. 결정 기록의 근거와 개별·최종 정답을 사전에 작성했다.
- 입력 스키마, 개별 정답을 주입한 실제 집계와 최종 정답의 정합성, 완전 중복을 검증했다.
- 별도 AI 검토자가 60개 시나리오 전체의 의미·근거·집계 라벨을 검토했다. Critical/Important
  지적은 없었고, WEATHER 문장의 대기 대상을 명시하라는 Minor 의견 1건을 반영했다.
- 사람의 라벨 승인을 받았거나 실제 게시글의 대표성을 검증한 데이터는 아니다.
- **v1.1(2026-10-14)**: 결정 기록 U11(같은 시각이면 댓글 우선, 같은 종류는 큰 ID)과
  U12(최신 유효 제보에 원인이 없으면 이전 원인 버림) 변경에 따라 049·051·052의 최종 정답만
  바꿨다. 요청 본문·개별 정답·load.json은 그대로다. 사례 ID는 기록 비교를 위해 유지했다.
  2026-10-13 기준선 보고서의 60/60은 v1 정답 기준이다.
- **v1.2(2026-10-14)**: 모든 원글 제목이 "현장 소식" 하나였던 것을 본문에 맞춘 실제 커뮤니티 글
  제목으로 바꿨다(quality 69개, load 공통 1개, requests/ 재생성). 제목은 본문보다 단계를 세게
  쓰거나 본문에 없는 원인을 넣지 않았다. 본문·정답·시각·ID는 그대로다. 제목도 LLM 입력이므로
  v1.1 이전 실모델 결과와 직접 비교할 때 주의한다.
- v1 정답과 이전 제목으로는 2026-10-13에 실모델 60사례를 평가해 최종 집계 60/60이
  일치했다. 이 결과는 제목과 정답 일부를 바꾼 현재 v1.2의 재평가 결과가 아니다.
  현재 v1.2는 실모델 재평가 전이며, 아래 검증 결과는 구조·집계 정합성 검사다.

## 1. 품질 데이터: 새 시나리오 60개·글/댓글 76개

| 유형 | 시나리오 수 | 확인할 내용 |
| --- | ---: | --- |
| 명확한 직접 단계 | 15 | LOW·MEDIUM·HIGH 각 5문장 |
| 명확한 직접 원인 | 10 | 구체 원인 코드 10종을 최소 한 번씩 포함 |
| 무관한 내용 | 8 | 일반 대화·생활 정보·혼잡과 연결하지 않은 날씨·행사 |
| 관련되지만 무효인 제보 | 8 | 질문·전언·예측·명시적인 과거 관찰 |
| 부모 글·댓글 | 6 | 댓글 자체 단계·원인, 부모 원인 복사 금지, 같은 작성자 |
| 작성자 집계 | 8 | 최신 제보·단계/원인 독립 선택·동률·동시각 충돌·원인만 있는 제보 |
| 시간 창 | 4 | 10분·60분, 오래된 부모, 창 양끝 경계 |
| 빈 스팟 | 1 | 모델 없이 UNKNOWN·0명·빈 원인 |

`quality.json`의 각 항목은 다음을 포함한다.

- `request`: 그대로 사용할 HTTP 요청.
- `annotations`: 원글/댓글 ID, 창 안 여부, 관련성 정답, 개별 단계·원인 정답, 결정 기록 근거.
- `expected_result`: 작성자별 집계까지 반영한 최종 단계·제보자 수·원인별 수.
- `category`, `rules`: 유형별 오류 분석과 라벨 검토에 사용할 분류·근거.

현재 분포는 최종 LOW 10·MEDIUM 19·HIGH 9·UNKNOWN 22시나리오다(v1.1).
글/댓글은 RELATED 64·UNRELATED 9·시간 창 밖 3개다. 관련성 후보는 73개이고 분포가
균등하지 않다. 단순 전체 정확도만으로 관련성 분류 성능을 판단하지 않는다.

검토 표는 [review.md](review.md), 전체 정답은 [quality.json](quality.json)에 있다.
기존 평가와 본문이 완전히 같은 항목은 없지만 표현·정책의 유사성은 남아 있다.
여기서 신규 평가셋은 기존 사례의 ID·시각만 바꾼 복제본을 의미하지 않으며 통계적 독립성이나
실제 사용자 분포의 대표성까지 보장하지 않는다. 76개 신호가 서로 완전히 독립인 것도 아니다.

### 보류한 경계 표현

초기 데이터 생성 시 경계로 분류한 “이동하기 힘들다/어렵다”, “이동 속도가 느리다” 등의
표현은 이 정답셋에 넣지 않았다. 이후 일부 표현의 기준이 정해졌지만 v1.2 라벨에 새로
반영하거나 과거 측정의 정확도 분모에 소급해서 더하지 않는다.

## 2. 속도·입력량 데이터: 6스팟 고정

| 글+댓글 합계 | 게시글 묶음 | 정상 분석 시 Decisions 호출 | 정상 분석 시 추출 호출 |
| ---: | ---: | ---: | ---: |
| 30 | 6 | 6 | 6 |
| 120 | 24 | 24 | 6 |
| 300 | 60 | 60 | 6 |
| 600 | 120 | 120 | 6 |
| 1,000 | 200 | 200 | 6 |

각 묶음은 원글 1개·댓글 4개다. 관련 비율 60%, 모두 서로 다른 합성 작성자이며
원글 MEDIUM·EVENT, 현장 댓글 MEDIUM·HIGH, 무관 댓글 2개로 구성했다. 스팟당 최종
MEDIUM, 혼잡 제보자 `3×묶음 수`, EVENT 제보자 `묶음 수`를 사전 정답으로 둔다.

부하 입력은 본문 5개를 반복하므로 정확도 독립 사례 수로 세지 않는다. 고정 구성에서
양이 늘어날 때 생기는 처리 시간·호출 수·실패·최종 집계 변화를 확인하는 입력이다.
실제 서비스의 본문 길이·작성자 반복·관련 비율을 대표한다는 뜻은 아니다.

1,000개는 현재 요청 스키마의 상한을 만족하는 스트레스 입력이며 처리 능력 보장이 아니다.
같은 스팟의 분류는 묶음별 순차 실행이므로 제보 수뿐 아니라 묶음 수도 함께 기록해야 한다.
전체 원본·정답은 `load.json`, HTTP에 바로 넣을 파일은 `requests/load-*.json`이다.

## 3. 평가 지표와 실행 순서

### 품질: 분류·판정·집계를 각각 보고한다

| 계층 | 지표 |
| --- | --- |
| 관련성 분류 | RELATED/UNRELATED 혼동행렬·precision·recall·F1·제외된 관련 후보 수 |
| 개별 단계 | LOW/MEDIUM/HIGH/보류 혼동행렬·정확도·macro F1·유형별 오류 |
| 개별 원인 | 원인 집합 완전 일치율·코드별 precision/recall/F1·코드별 정답 건수 |
| 최종 스팟 | 단계 혼동행렬·정확도·제보자 수 절대 오차·원인별 수 오차·전체 결과 일치율 |
| 실패 | 전체 요청/스팟 실패 건수와 비율·실패한 단계 |

분류에서 제외한 글을 “LLM이 맞힌 null”로 세지 않는다. 실제 선택된 개별 판정의 점수와
관련 제보 누락을 포함한 전체 흐름의 결과를 따로 보고한다. 기술 실패도 최종 결과 일치율의
분모에서 빼지 않는다. 원인 없음 판정이 많아서 점수가 높아지는 효과를 코드별 지표로 확인한다.
각 코드의 양성 사례가 적으므로 단일 코드의 안정적인 정확도 추정으로 과장하지 않는다.

처음에는 현재 프롬프트를 고정한 채 60시나리오를 평가한다. 결과를 보고 프롬프트를 바꾸면
이 데이터는 이후 회귀셋으로 사용하고 다음 검증에는 추가로 보지 않은 사례를 확보한다.
합성 데이터에서 확인할 수 있는 것은 정의한 규칙의 구현 품질이며, 실제 게시글 정확도는
사람이 라벨링한 실제 데이터로 별도 확인해야 한다.

### 속도·양: 작은 요청부터 단계적으로 실행한다

1. 30·120개 입력을 먼저 실행해 오류·호출량·시간을 확인한다.
2. 같은 서버·worker 1·모델·설정·본문·작성자 비율에서 반복 측정한다. 입력량 비교 중
   프롬프트나 분류 임계값을 바꾸지 않는다.
3. 이후 300·600·1,000개로 확대하며 실패·대기시간 증가를 기록한다. 큰 입력까지 모두
   곧바로 실행해야 한다는 뜻은 아니며, 측정은 작은 요청에서 확인한 시간·비용을 보고 확대한다.
4. 요청 전체 왕복, 분류/추출 시간, 입력 수, 묶음 수, 실제 호출 수, 토큰·캐시 사용량,
   성공/실패, 최종 정답 일치를 함께 기록한다. 성공 요청의 시간만으로 결론을 내리지 않는다.
5. 처음 몇 회의 중앙값·범위·최대값은 탐색 결과다. 반복 횟수를 공개하고 운영 p95나
   동시 요청 처리량으로 확대 해석하지 않는다. 요청 간 동시 부하 평가는 별도다.

Spring의 실제 최대 입력량·응답 대기시간이 미합의이므로 현재 이 데이터만으로 운영 합격선이나
전체 타임아웃을 정하지 않는다. 60개·다섯 입력량은 이번 데이터 구성값이며 운영 요구값이 아니다.

## 4. 검증과 직접 보기

다음 검증은 네트워크·API 키·모델 호출 없이 실행한다.

```sh
.venv/bin/python examples/congestion/dataset-v1/validate_dataset.py
```

현재 결과는 입력 60시나리오·부하 5종 유효, 기존 본문과 완전 중복 0,
정답 집계 정합성 검사 90건 통과다. 이는 모델 정확도 90/90이라는 의미가 아니다.

Swagger에 바로 넣을 예시는 `requests/quality-sample.json`이다. 사전 정답은
MEDIUM·제보자 1명·EVENT 1명이다. `requests/load-30.json`은 6스팟에 각 5개 신호가 있으며
스팟마다 MEDIUM·제보자 3명·EVENT 1명이 사전 정답이다. 실제 API 실행에는 비용이 발생한다.

`build_dataset.py`는 데이터 생성 초안을 만들고 기존 파일이 있으면 덮어쓰지 않는다.
라벨 의미 검토를 별도로 진행한 후 manifest 상태를 갱신한다. 현행 파일은 별도 AI 검토의
수정 1건을 반영하고 SHA-256을 저장한 상태다. `validation.json`이 구조 검증 기록이다.

데이터셋 생성 작업의 범위는 생성·검토·오프라인 검증까지였다. 당시 제품 코드·프롬프트·테스트·환경설정·
의존성은 변경하지 않았고 실제 모델은 호출하지 않았다. docs는 기존 지침대로 커밋하지 않는다.

`manifest.json`과 `validation.json`의 모델 호출 0은 이 생성/오프라인 검증 시점의 기록이다.
정답과 정본 해시를 고정하기 위해 이 파일들을 후속 평가 누적값으로 덮어쓰지 않았다.
실제 실행별 호출·점수·시간·사용량은 별도 기준선 결과 폴더에서 확인한다.
